# Phase 3 completion report — Verified Action Runtime

**Status: complete for the implemented providers, with the concrete remaining provider constraints recorded below. Ready to begin Phase 4 when the user supplies the Phase 4 instruction.** Phase 4 implementation has not started. Validation date: 2026-10-04; workspace: `E:\MORICE`, Windows, repository virtual environment, PySide6 6.11.2.

1. **Phase 1 foundation status.** The existing CapabilityKernel, capability registry, typed task/results, verification contracts, permissions, cancellation, process ownership, patch UndoStore, and node-scoped resource leases remain authoritative. No replacement kernel or separate execution boundary was created.

2. **Phase 2 foundation status.** `morice/agent_runtime/`, TaskGraph, WorkerManager, AgentCoordinator, SharedTaskState, nine production roles, compact contexts, workflow limits, checkpoints, shared model routing, and lazy bounded pools are retained. Workers execute through the same kernel and Phase 3 bindings.

3. **Repairs.** Requested-URL caching was removed as false observation. Application readiness requires actual usable windows. File existence no longer proves viewer success. Process-family observation handles Windows Python launch redirectors. Scheduler admission avoids dispatching normal resource contenders into workers. Browser search respects its original query schema and PC permission broker. Qt DOM result serialization, page ownership, shared-profile download isolation, project-claim fingerprinting, and cancelled journal IDs were repaired through integration and regression checks.

4. **Architecture.** `VerifiedActionRuntime` is an optional extension on the existing kernel. Registry bindings supply desired state, independent observation, and domain verification. Kernel gates, executor ownership, retry policy, final result, and resources remain shared. The architecture diagram and integration examples are in `verified-action-runtime.md`.

5. **Action contract.** ActionSpec records action/task/goal/target/capability/method/desired state, verification level, bounded observation policy, rollback reference, and structured expected outcome. Observation supplies source, timestamp, state, evidence, errors, confidence, and raw reference. Existing ExecutionResult and VerificationResult represent the final outcome.

6. **Desired state.** Application goals describe usable/focused/restored/closed windows; browser goals describe actual URL, DOM value/text, page generation or tab identity; files describe hashes/size/existence; terminal commands require observed exit code zero; media describes actual volume/playback/track state. Idempotent goals already met are verified no-ops. Extra kernel expected-outcome fields must also match fresh state.

7. **Observation architecture.** Before and after observations come from actual Win32 windows/process identities, QWebEngine callbacks and DOM, streamed disk bytes, owned process completion, and media-session queries. Missing, stale, future-dated, mismatched, or erroneous observations cannot certify success. Vision is separately identified as a hypothesis.

8. **Verification architecture.** Deterministic domain checks override apparent provider success. Nonzero exit, wrong URL, unready page, wrong process/window, corrupt hash, partial download, and unobservable viewer association fail or remain inconclusive. Confidence does not establish success. NONE cannot certify a mutable operation; other current levels share minimum independent proof rather than claiming stronger application-specific assurance.

9. **Recovery architecture.** Existing kernel retries can select explicitly declared distinct registered alternatives after eligible failures, including an unavailable primary. Each alternative receives the same schema, health, permissions, cancellation, and resource checks. Every attempt records its actual result. Interrupted checkpoint recovery reads current state without replaying a mutation.

10. **Execution method hierarchy.** Contracts name application API, OS API, filesystem, CLI, browser DOM, accessibility, foreground control, and vision. Installed bindings use existing application/OS/filesystem/CLI/DOM methods. No accessibility, general input, or model provider is fabricated when absent. Alternatives are explicit rather than selected by an unconstrained planner.

11. **Desktop providers integrated.** Existing ApplicationManager and WindowManager actions cover open/focus/restore/maximize/minimize/close/close-others. Win32 observations include process image/family, handle, geometry, enabled/visible/minimized state, DPI, and monitor. Ambiguous matches and save dialogs block for review. Bulk closing preserves MORICE and the requested exception.

12. **Browser providers integrated.** The existing AssistantHub QWebEngineView/profile supports observed navigation, back/forward/reload, find/click/type/submit/extract, owned tab control, and completed downloads. Semantic locators tolerate changed element IDs in the real fixture. Generic click and submit require user-declared observable outcomes and exact confirmation. Upload is registered but explicitly requires user intervention; it is not claimed as automated. External system-browser launch remains inconclusive without DOM access.

13. **File verification improvements.** Patch and artifact checks stream actual bytes, SHA-256, size, and existence; partial-file suffixes cannot verify. Existing undo is checked against restored/deleted files. Viewer opening requires document association with a usable owned viewer window. Default shell association can remain inconclusive because `os.startfile` exposes neither reliable viewer PID nor document identity.

14. **Process verification improvements.** Terminal verification uses actual owned process completion, exit code, cancellation/timeout flags, and stdout/stderr retained by the existing adapter. A real successful test/build writes an artifact; an independently observed result window then proves application readiness. No simulated test/build output is used.

15. **Foreground resource behavior.** Existing exclusive FOREGROUND_UI ownership protects desktop window control. Browser and media session claims use the same ResourceManager. Terminal tasks add a bounded, hashed per-workspace PROJECT_BUILD claim before graph fingerprints are taken. Ordinary parallel contention waits in scheduler admission, outside task worker slots.

16. **Focus protection.** FocusGuard checks the intended observed handle before foreground input and stops on focus theft. It restores only while MORICE still owns the target and does not fight user focus. Tests inject stolen focus. Current browser typing targets its DOM element; no generic desktop keyboard/mouse provider was added or claimed as verified.

17. **Multi-monitor/DPI handling.** Geometry conversion uses observed physical rectangles, DPI, and monitor identities, including negative coordinates. Tests cover 96/120/144 DPI and negative-monitor layouts. Real owned viewer windows were observed at 120 DPI. Multiple physical monitor configurations were not exercised on hardware.

18. **Vision fallback behavior.** `vision.screen_observe` reuses the existing LiveVision provider and kernel screenshot capability, with screen/vision permissions and the shared GPU claim. It validates screenshot/frame/target identity and caches eight matching frames. Output is a semantic hypothesis with `usable_for_action_verification=False`. No compatible local model/projector was configured, so real semantic inference remains unvalidated; there was no model download or extra runtime.

19. **Accessibility/DOM support.** Browser DOM supports unique role/name, ARIA/label, test-ID, and explicit-selector matches. Input strings are quoted data. Full Windows UI Automation is not installed. Cross-frame/shadow DOM and application-specific accessibility providers remain unsupported rather than guessed from screenshots.

20. **Retry limits.** Existing RetryPolicy bounds attempts and retryable error classes. Phase 2 retains its workflow/task/depth/retry budgets. Repeating the identical failed action without a distinct declared alternative is suppressed. Duplicate or self-referential alternatives are rejected. Default observation bounds are three seconds/40 polls, clamped to ten seconds/100 polls and the kernel deadline.

21. **Alternative method behavior.** The real recovery demo declares an unavailable preferred application capability and a healthy alternative that launches an actual owned viewer. It succeeds on the second attempt with fresh Win32 evidence; both attempts are journaled. Negative tests cover unavailable alternatives, denied alternatives, identical alternatives, and exhausted recovery.

22. **Cancellation behavior.** Stop propagates the existing action/workflow token. Queued Qt operations check cancellation before mutation; late replies cannot change final history. Downloads cancel, and owned process trees are terminated and reaped. Cancelled scheduler reservations release when not started; actual work owns its lease until it stops. The inline-observer cancellation regression confirms the original journal attempt is finalized rather than left interrupted.

23. **Timeout behavior.** Observations use adaptive cancellable waits and the existing kernel deadline. Native work that ignores cancellation can detach; its lease remains reserved until it actually exits. This is an explicit limitation of interrupting Python/native API calls, not evidence of successful cancellation. Final timeout/cancellation cannot be overwritten by late verification.

24. **Rollback support.** Explicit workflow-owned rollback dispatches the existing action.undo capability with fresh approval and UndoStore hash/ownership checks. Verification independently checks restored contents or deletion. Arbitrary application/network/external side effects cannot be undone automatically. Checkpoint restoration never assumes that blind replay is rollback.

25. **ActionJournal.** A bounded sidecar records attempt method, authorization/resource facts, pre/post state, verification, errors, recovery, and timing beside existing final ActionHistory. Executing intent is durable before mutation; final outcomes are atomically persisted. Secret keys and URL credentials are redacted; value/text/content/goal fields are omitted. It does not create another final history or copy complete screens, pages, prompts, or command output. Filtering is field-based and does not promise comprehensive secret detection.

26. **Prompt-injection protections.** Browser/UI text remains evidence and cannot authorize actions, install methods, modify policies, or become a system instruction. DOM input/locators are quoted as data. Expected outcome is supplied by the task, not page instructions. Tests include hostile page text, incorrect expectations, and permission denial despite broader native grants.

27. **Permissions/risk integration.** Existing centralized policies and PC confirmation remain authoritative for every method and alternative. Generic click/submit/upload and close-others require exact high-risk confirmation. Filesystem changes, terminal execution, screenshots, vision, downloads, and rollback retain their existing permission categories. Login/OTP/CAPTCHA or blocked/save-dialog states request user intervention without automatic bypass.

28. **Phase 2 worker integration.** Browser role capabilities extend to registered browser actions; verifier includes artifact.verify and vision includes vision.screen_observe. WorkerManager passes only the internal reservation needed for shared lease adoption along with its compact context. The real demo runs browser, file-reader, and owned-desktop workers through existing AgentCoordinator/TaskGraph/SharedTaskState, with successful outcomes and zero remaining leases.
